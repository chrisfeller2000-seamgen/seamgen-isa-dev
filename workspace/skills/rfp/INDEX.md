# RFP playbook

Read this for any RFP request. It takes priority over older RFP notes in `memory/` and over any other RFP skill or workflow (such as `rfp-flow`). Each skill has its own folder, `skills/rfp/<skill>/instructions.md`; open the one named and follow it, don't do the task from memory.

## Every RFP message: run the router first

Run the router with their message, exactly as written, on standard input:

```
node scripts/rfp-route.mjs <<'RFP_MESSAGE_END'
<their message>
RFP_MESSAGE_END
```

Never put a person's message inside quotes on the command line: quotes, `$(` or backticks in it would run as commands. The router's own `route` commands are safe to run as they are. It decides which skill, which RFP and which phase are meant, and prints one JSON decision. Do what its `action` says:

| `action` | What you do |
| --- | --- |
| `run-skill` | Open `skill.file` and follow it for `rfp`, reading the RFP's saved documents first with the commands in `documents`. |
| `ask-move`, `ask-which-rfp`, `ask-which-phase`, `offer`, `already`, `retired`, `unknown-command` | Send `say` word for word, and nothing else. |
| `move` | Run `command` with the person's name in `--by`, then pass on what it prints: that it moved, and the list of the new phase's skills word for word. If it refuses, pass on its reason. |
| `list` | Run `command` and answer from it, using phase names. |
| `answer`, `share-documents`, `rescore` | Follow `note`, using the sections below and the RFP's `documents`. |
| `needs-context` | They answered your last question ("yes", "no", "keep it where it is", a number). Find the choice they picked in that question and run its `route` command. "Yes" is choice 1; "no" or "keep it" is the choice that leaves the RFP where it is. |
| `none` | It isn't an RFP request. Answer normally. |

Each choice in a decision carries `route`, the exact router call for it. When choice 1 of a move question is taken, run its `route`, and once the RFP has moved, run its `thenRoute`. Never say an RFP moved unless `rfp-stage.mjs` printed that it did.

## Commands people can use

Your questions and offers show these next to each choice, so people learn them by replying:

- `rfp <command> <rfp>`: run a skill for an RFP, for example `rfp brief laguna-beach-website-redesign`. Add `--stay` to run a later-phase skill without moving the RFP.
- `rfp move <rfp> <scored|looking|building|submitted>`: move an RFP.
- `rfp skills <rfp>`: what can be done for it in its phase.
- `rfp list`: which RFPs we're working on.

## Phases

| Phase | Folder | Means |
| --- | --- | --- |
| Phase 1: Scored | `1-pre-submission` | Every RFP whose documents the Friday job saved |
| Phase 2: Looking closer | `2-intermediate-stage` | Someone decided to look closer |
| Phase 3: Building | `3-building` | The proposal is being written |
| Phase 4: Submitted | `4-submitted` | The proposal went in |

The router applies the phase rules: a skill from a later phase than the RFP's asks about a move first (the submission email never does), a skill from the RFP's phase or an earlier one just runs, and after a move it lists the new phase's skills. A phase never blocks a skill: `--stay` runs it in place.

## Scoring and filtering

- **Where the results are:** this week's results are in `reports/new-rfp-qualification/latest.json`, with one entry per RFP: tier, score, what they want, why we fit, blockers, open questions, deadline, budget and links. Its `email` record holds what was sent: subject, recipients and text. Its `inProgress` list names RFPs already in Looking closer, Building or Submitted whose HigherGov listing changed that week; they aren't scored or picked again, because the Tuesday check covers them. The same report is in `latest.md`. Each RFP's scoring detail is in `RFP-pipeline/candidates/<slug>/candidate.md`, which the Friday job clears each week; an RFP someone moved to a later phase keeps a copy as `candidate.md` in its `RFPs/<folder>/<slug>/` folder.
- **Answering questions:** when someone asks about an RFP, answer from those files in the same voice as the Friday update. Keep it short and use plain words, the Drive folder or HigherGov link, and "estimate" for HigherGov budgets. Never paste file paths, internal codes, or rubric terms like "gate".
- **Questions about the pursue email:** answer from its `email` record. Never resend it, and don't change any files, HubSpot, or other records.
- **Rescoring one RFP:** when someone asks to rescore a specific RFP from this week's results, use `scripts/rfp-rescore.mjs`, never the weekly job. First run `node scripts/rfp-rescore.mjs <slug>` (the slug is the RFP's `slug` in `latest.json`) and tell them the before and after in plain words; that changes nothing yet. Only after they confirm, run `node scripts/rfp-rescore.mjs <slug> --apply`, which puts the new result in this week's report. Add `--drive-folder <link>` to the first command when they give you the RFP's Drive folder. A rescore never sends the pursue email or posts to the group: say so, and don't offer to send the email yourself. It only works for this week's RFPs whose documents were saved; if it says it can't, pass on its reason.

## Scheduling

- **The Friday job** (`scripts/weekly-rfp-pursue-decision.mjs`) scores the week's RFPs at noon Pacific, emails Marianne and Sales about the Strong Pursue ones, and posts a summary in the sales group that offers to move them to Phase 2. Never run it unless someone explicitly asks: running it again replaces that week's report.
- **The Tuesday check** (`scripts/rfp-refresh.mjs --scheduled`) runs every Tuesday morning for the RFPs in Phases 2 and 3: it saves new documents, puts them in each RFP's Drive folder, and posts one message in the sales group only when something changed. Never run it yourself; its results are in `reports/rfp-refresh/latest.json`. New documents aren't a skill to offer: this covers Phases 2 and 3 on its own.
- **Checking one RFP now:** when someone asks, run `node scripts/rfp-refresh.mjs <slug>`; it never posts to the group.
- **An RFP's dates:** the router's `answer` carries `dates` when the RFP has a key-dates note: the dates read from its documents, with weekdays and time zones worked out and `passed` marked. Answer from those, with their source. With no `dates`, read the documents and give each date as printed, with the file and page; never a date from the HigherGov listing or the scoring. Never work out a weekday or a "days left" count yourself when `dates` has it. To put dates on someone's calendar, use the calendar skill (`rfp dates <rfp>`): `scripts/rfp-dates.mjs` writes a calendar file to attach. ISA never writes to a calendar itself.

## Documents

- **Original RFP documents:** when you download an RFP document or someone sends you one, save it in that RFP's `RFPs/<folder>/<slug>/resources/` folder before you read it, following `skills/rfp/document-fetch/instructions.md`. When you clean up after a task, remove only working files you made in that task, and never trash or delete anything in a `resources/` folder. The only time an RFP's documents are removed is the no-bid purge in that skill.
- **Reading an RFP's documents:** the router's `documents` lists what is saved for the RFP, numbered. Read them with `node scripts/document-text.mjs --rfp <slug> --file <number>` (or `--file all`), and its scoring notes with `--notes`. Pick documents by number: never put a file name or path in a command, because agency file names can contain characters a shell would run. Never ask the person for a document that is already saved. When `documents.saved` is 0, follow `skills/rfp/document-fetch/instructions.md` first, and ask only if that fails.
- **Sharing a document:** when someone asks for an RFP document, attach the file in the chat. Say it is in Drive only when a Drive link for that RFP says so, and never give a path on your own disk as a link.
- **Putting documents in Drive:** each RFP has one Drive folder under Sales › Favorable RFP's, whatever phase it is in. To upload an RFP's documents there, run `node scripts/rfp-refresh.mjs <slug> --drive` and share the folder link it prints. It uploads only the agency's documents the folder doesn't have, and never replaces or deletes anything in Drive. Never upload to Drive any other way.

## Writing

- Every email for an RFP is given as text to copy. Never create a Gmail draft or send it, and leave the signature for the sender to fill in.
- **Agency Q&A questions:** start with the questions deadline, give the questions with the RFP text behind each, then the email.
- **The email that goes with a proposal:** never write it freehand; the skill first checks whether the RFP allows email at all, and asks about Submitted after sending.

## Tracking

- **Moving an RFP:** only when someone asks, or says yes to your question, through the router's `move` decision. Never move or copy an RFP folder any other way, and never create one directly in a later phase: an RFP with no folder yet (one someone sends you, say) goes in `RFPs/1-pre-submission/<slug>/`, and `rfp-stage.mjs` moves it from there. Moving back to Phase 1 means nobody is working on it any more.
- **Forwarded RFPs:** when a move prints that the RFP has no HigherGov listing key, find its agency and solicitation number in its documents and record them with `node scripts/rfp-stage.mjs <slug> --agency "<agency>" --number "<number>" --by "<their name>"`; ask the person if the documents don't say. That is how the Friday run recognizes its listing if it reaches HigherGov.
